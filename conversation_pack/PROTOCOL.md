# Conversation Pack Protocol v0.2

本协议用于把一个**尚未结束但需要换窗口继续的 AI 对话**迁移到新对话。

核心原则只有一句：

> **GPT 负责盘点，用户负责筛选，脚本负责搬运。**

Conversation Pack 不追求保存完整聊天，也不要求 GPT 建立复杂的节点图、价值评分或自动记忆系统。

## 1. 什么时候进入迁移流程

当用户表达类似意图：

- “总结一下，准备换对话。”
- “把当前关键信息和文件整理出来。”
- “准备迁移到新窗口。”

GPT **不要立即生成 ZIP 或全部结果文件**，而是先进入 Preview。

## 2. Stage 1 — Preview

Preview 的目的不是替用户决定，而是把当前对话盘点清楚，让用户快速拍板。

固定包含三部分。

### A. 当前状态

简要回答：

- 当前在做什么；
- 已经做到哪里；
- 下一步是什么。

不复述完整历史。

### B. 文件 / 产物盘点

GPT 整理当前对话中与后续可能有关的文件、数据和产物，优先按**类型 + 实际名称**列出，例如：

```text
模型结果
- WRF 当前结果：xxx.csv
- ADCIRC 当前网格：fort.14

验证数据
- 真值：xxx.xlsx
- 模拟值：xxx.csv
- 统计结果：xxx.xlsx

绘图
- 最终绘图脚本：plot_validation.py
- 配置：config.json
- 最终图：validation.svg
```

用户往往只会说“保留验证数据、模型结果、最终绘图流程”这类类别，不要求用户记住具体文件名。GPT 应回溯当前对话，把类别尽量解析为实际文件或明确的产物类型。

如果无法确定具体文件，不要猜，标记为“待确认”。

### C. 关键信息候选

只列下一对话继续工作需要的有效信息，例如：

- 当前工作状态；
- 用户已经确认的规则或决定；
- 当前仍有效的分析结论；
- 需要避免重复的关键纠正；
- 下一步任务。

默认不保存原始聊天摘录。

## 3. 文件选择原则

文件是否进入 Pack，最终由用户决定。

GPT 只做轻量判断：

### 建议列为候选

- 用户明确要求后续继续使用的文件或文件类别；
- 当前任务尚未结束且下一对话仍需使用的输入数据；
- 当前对话生成、且后续仍需复用的结果文件；
- 已经成为后续工作基线的脚本、配置、图表或处理结果。

### 默认不建议迁移

- 只为本对话临时排错使用、问题已结束的截图或日志；
- 已经被新版完全覆盖的旧文件；
- 后续不会再使用的中间产物；
- 可由新 GPT 重新完成、且不依赖独有文件状态的普通问题解决过程；
- 完整聊天原文。

**注意：文件“不可复现”本身不构成保留理由。若后续不再使用，就没有必要迁移。**

## 4. 用户裁决优先

优先级固定为：

```text
用户本次迁移时的明确要求
    >
用户在当前对话中已经确认的要求
    >
GPT 的自动整理和建议
```

典型审批方式可以非常简短：

- “都保留，ADCIRC 中间结果不要。”
- “只留验证数据、最终 SVG 流程和当前模型结果。”
- “按你列的生成，再加上那份清洗后的数据。”

用户没有确认前，不进入正式 Build。

## 5. Stage 2 — Build

用户确认后，GPT 生成两类输入：

### `HANDOFF.md`

只保存用户确认后的有效信息，建议结构：

```markdown
# Handoff

## 当前任务

## 当前状态

## 需要继承的关键信息

## 已确认规则 / 结论

## 下一步

## 携带文件说明
```

不保存完整聊天原文，也不要求保留“用户说了什么 / GPT 原话是什么”的逐轮记录。

### `spec.json`

只列用户确认要携带的实际文件。

示例：

```json
{
  "schema_version": "0.2",
  "pack_name": "example_handoff",
  "handoff": "HANDOFF.md",
  "assets": [
    {
      "source": "source/current_truth.xlsx",
      "target": "files/current_truth.xlsx",
      "label": "当前真值数据",
      "role": "validation_data",
      "required": true
    }
  ]
}
```

## 6. Stage 3 — Deterministic packaging

`build_pack.py` 不理解对话，只完成确定性操作：

- 检查 `HANDOFF.md`；
- 检查用户确认的文件是否存在；
- 复制文件；
- 计算 SHA-256；
- 生成 `manifest.json`；
- 生成 `QA.md`；
- 可选输出 ZIP；
- 不修改源文件；
- 不把本机绝对源路径写入最终 manifest。

最终结构：

```text
conversation_pack_xxx/
├── HANDOFF.md
├── manifest.json
├── QA.md
└── files/
    └── ...用户确认的文件...
```

## 7. 新对话接管

新对话首先读取：

```text
HANDOFF.md
```

随后只按任务需要读取 `files/` 中的具体附件。

Conversation Pack 的目标是传递**当前有效状态**，不是让新对话重新学习旧对话全过程。

## 8. 设计边界

- 不保存完整聊天原文作为默认方案；
- 不建立复杂的自动价值评分系统；
- 不要求用户自己列出精确文件名；
- GPT 不应编造未确认的文件名或文件内容；
- 不因文件曾上传或生成过，就自动将其保留；
- 不把一次性项目规则自动提升为长期用户记忆；
- Conversation Pack 与未来的 `ai_memory` 是两个独立问题。

## 9. 当前试验重点

v0.2 先验证三个问题：

1. GPT 能否可靠盘点当前对话中的文件 / 产物类型和名称；
2. 用户是否能用很少的回复完成筛选；
3. 新对话只读 `HANDOFF.md` + 用户确认文件后，是否可以继续工作。

后续只根据真实迁移问题修订协议，不为理论完备性增加复杂结构。
